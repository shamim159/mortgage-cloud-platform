# Synthetic Mortgage Applicant Dataset

## Provenance

**Every record in this dataset is synthetic.** No real person, property or loan is represented.

- Applicant IDs all start with `SYN-`, so a row is identifiable as synthetic on its own.
- Surnames come from a hand-written list of fictional names (e.g. `Testwell`, `Mockford`, `Notrealson`), not from Faker.
- First names come from the Faker library (`en_GB` locale). A first name may match a real one, but combined with a fictional surname it never identifies a real person.
- All numbers and dates are randomly generated by the script.

## Files

| File                             | Description                                     |
| -------------------------------- | ----------------------------------------------- |
| `scripts/generate_applicants.py` | Generator script                                |
| `data/applicants.csv`            | 500 applicants, one row each, with a header row |
| `data/applicants.json`           | The same 500 records as a JSON array of objects |

## Regenerating

```bash
source .venv/bin/activate
pip install faker
python scripts/generate_applicants.py
```

Run from the repo root. The script seeds both Python's `random` module and Faker with `42`, and the application date window is fixed, so every run produces identical files. Changing the seed produces a different but equally reproducible dataset.

## Schema

One record per mortgage application. Money values are in whole pounds (GBP).

| Field              | Type    | Description                                    | How it's generated                                                             |
| ------------------ | ------- | ---------------------------------------------- | ------------------------------------------------------------------------------ |
| `applicant_id`     | string  | Unique ID, e.g. `SYN-0001`                     | `SYN-` plus a zero-padded sequence number, 0001 to 0500                        |
| `full_name`        | string  | Applicant name                                 | Faker first name + random fictional surname                                    |
| `annual_income`    | integer | Gross annual income                            | Random whole number from 20,000 to 150,000                                     |
| `loan_amount`      | integer | Amount borrowed                                | **Calculated:** `annual_income` x a random multiplier between 3 and 5, rounded |
| `ltv`              | decimal | Loan-to-value ratio as a fraction (0.86 = 86%) | Random between 0.60 and 0.95, rounded to 2 decimal places                      |
| `property_value`   | integer | Property price                                 | **Calculated:** `loan_amount` / `ltv`, rounded                                 |
| `application_date` | string  | Date of application, `YYYY-MM-DD`              | Random date within a fixed two-year window ending 2026-10-01                   |

`loan_amount` and `property_value` are derived from other fields so the numbers stay consistent. Generation order is income, then loan, then LTV, then property value.

Because `property_value` is calculated from the unrounded LTV, `loan_amount / property_value` can differ from the stored `ltv` in the second decimal place.

## Caveats

- **Not for modelling.** There is no real relationship between applicant characteristics and outcomes, and there is no approval or credit data. Do not use this to train or evaluate an approval or risk model.
- **Unrealistic distributions.** Every value is drawn uniformly from its range. Real incomes, loan sizes and LTVs are skewed and correlated in ways this data doesn't reproduce.
- **Simplified lending rules.** Affordability is a single income multiple. There are no deposits, credit scores, terms, interest rates or regional price effects.
- **Dates are a fixed window,** not a reflection of real application volumes or seasonality.

## Notes for DynamoDB / RDS

- `applicant_id` is unique and works as the DynamoDB partition key or the RDS primary key.
- Load from the JSON file where possible. It keeps numbers as numbers, while CSV loaders often need explicit type conversion.
- If you query by date, `application_date` is stored as ISO text, which sorts correctly as a string. It could serve as a sort key or a GSI key.
